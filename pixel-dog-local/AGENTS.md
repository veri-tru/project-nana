## 현재 화풍 기준: 기존 품종 B2 시안 정본

2026-11-07 사용자 “c를 정본으로하자”에 따라 두 개체 개인화의 현재 정본은 **pair-b2-retry04의 C / individual-pair-b2-C-v1**이다. [선택 기록](config/individual-pair-canonical.json)의 비공개 원본 이미지·해시를 따른다. 01/02 두 행과 5시점 전체의 털 덩어리·면 구분·귀/목/상흉부 표현이 선택 범위다. 해당 두 개체 후속 작화에는 실제 C 이미지를 참조로 전달한다. 아래 품종 공통 B2 화풍 기준을 바탕으로 한 선택이며 native64 승인이나 다른 품종 형상 교체를 뜻하지 않는다.

2026-11-06 사용자 지시 “기존 시안으로 정본화하고 다시만들어”에 따라 직전 비교의 **B2 / SOFT PIXEL 품종 시안**을 머리 픽셀 표현의 현재 정본으로 사용한다. [정본 manifest](references/styles/breed-head-b2/v1/manifest.json)와 [현재 규격](docs/b2-c2-style-spec.md)을 따른다. 픽셀 밀도·유색 윤곽·둥근 눈·부드러운 연결 음영을 실제 정본 이미지와 대조하며, 다른 품종들과 나란히 검토한다. 골든 비율은 수정 adult-B 모델을 사용하고 정본 속 과거 골든 형상으로 되돌리지 않는다. 기존 B2/C2 v1 참조는 이력으로 보존하고 C2는 현재 기본값으로 적용하지 않는다.

정본화는 화풍 선택이다. 고해상도 정본 이미지를 실제 64×64 실행 자산이라고 표시하지 않는다. 앱의 native64 목표는 유지하며 변환 출력은 정본과의 화풍 일치를 별도로 통과해야 한다. `golden-pixel-refresh-20261106`의 P1/P2/P3는 화풍 불일치로 사용자 거절된 결과다.

## 활성 엔진과 보존본

2026-11-12부터 Windows 실행·검증은 프로젝트의 `./engine.ps1`을 기본 진입점으로 사용한다. 최초 준비는 `./engine.ps1 -Setup`, 상태·환경·전체 검사는 각각 `status`, `doctor`, `verify`다. 내부 `.venv`는 Python 3.12와 `tools/dog_engine/verification-lock.txt`의 버전을 사용한다. 전역 Python의 설치 버전을 프로젝트 기준으로 바꾸거나 저장된 기준 이미지를 덮어써 재현성 실패를 해소하지 않는다. 직접 Python을 호출해야 하면 `.venv/Scripts/python.exe`를 사용한다. 현재 구현 요약은 `docs/current-spec.md`와 실제 `status`를 우선하고 날짜별 작업 기록은 당시 범위로 읽는다.

현재 실행 진입점은 `python -m tools.dog_engine`이며 [엔진 구조·상충 정리](docs/engine-organization.md)를 먼저 확인한다. `tools/head_engine`과 `outputs`의 기존 모델·생성 코드·검토 기록은 해시가 고정된 보존본이다. 새 실행 코드는 보존본의 생성 모듈을 import하지 않는다. 머리 3D 투영과 2D 전신 작화 경로는 별도이며 아직 연결되지 않았다. 구조 정리만으로 거절된 native64 화풍이나 미선택 후보를 승인하지 않는다.

## 제품 범위

- 개를 대상으로 실제 외형과 관찰된 행동을 반영합니다. 고양이는 후속 범위입니다.
- 픽셀 캐릭터의 기본 애니메이션은 8fps, 기본 프레임 간격은 125ms입니다. 동작당 프레임 수는 별개입니다.
- 픽셀 정본은 프레임당 64×64px입니다. 96×96 제작기 출력과 고해상도 화풍 시안은 참고 자료이며, 정본은 실제 64×64 격자에서 검수합니다.
- 첫 구현은 Android G0입니다. Kotlin 네이티브 표시 검증이 기본안이며 최종 공통 UI 프레임워크는 미정입니다.
- G0은 임시 캐릭터, 걷기·쉬기·잠든 자세, 탭·드래그·표시·종료를 검증합니다. 서버나 AI 연결은 G1 범위입니다.
- iOS와 Android의 표시 기능을 동일하다고 가정하지 않습니다. 홈 위젯을 연속 애니메이션 표면으로 전제하지 않습니다.

## 이미지 제작과 비교

### 2026-11-07 귀·목 구조 오류 재발 방지

사용자 지적 “뒷통수와 귀가 합쳐진 모습”, “목위치가 개가 아니라 사람”, “재발방지해”를 [구조 회귀 규칙](docs/anatomy-regression-policy.md)에 반영했다. 개체 작화와 머리–귀–목 변경은 **완전한 머리·목·어깨 구조 검토 → 작화 → 최종 전체 외형 재검토** 순서를 따른다. 귀 부문 PASS나 짧은 목만 있는 과거 모델 PASS를 전체 구조 승인으로 승계하지 않는다.

작화 전에 `python -m tools.dog_engine structure-gate --status <구조 review-status.json> --contract <structure-contract.json> --output-plan <새 appearance-plan.json>`이 통과해야 한다. 실제 image_gen 호출 직전에는 `structure-gate --plan <계획> --generation <호출인수JSON>`을 통과하고 검사한 동일 payload를 도구에 전달한다. 게이트 실패 시 원인 수정·검토를 계속하며 이미지 생성 재시도로 건너뛰지 않는다. 최종 작화는 같은 명령에 `--art-status <최종 review-status.json>`을 더해 전체 범위의 재검토를 확인한다. 이는 형상 자동 판정이나 외부 호출 자동 감시가 아니며 실제 호출 기록은 기술 리뷰에서 대조한다.

필수 근거: 동일 실제 메시의 정면·사선·측면·후면·윗면, 어깨·상흉부까지의 연결, 귀를 숨긴 진단, **동일 메시·카메라·배율의 짧은 crop/넓은 crop 비교**. 외형과 기술 보고서 모두 귀뿌리/자유 가장자리·독립 후두부·턱뒤–목앞·목뒤–등·목앞–가슴·받침대형 목 부재를 명시적으로 판정한다. 좌우 중심 목을 잘못이라고 일반화하거나 목을 단순히 옮기고 기울여 완료 처리하지 않는다.

image_gen 후보는 선언한 파라미터 외 형상이 달라질 수 있다. 실제 결과가 통제되지 않았다면 정밀한 수치 비교라고 표시하지 않는다. 엔진의 실제 표면 문제와 image_gen 입력/구도 문제를 구분하며, 생성 모델 내부 원인을 확정하지 않는다. 사용자 거절 해시와 후속 독립 FAIL은 보존하고 동일 결함을 좁은 검토 범위로 제외하지 않는다.

2026-11-05 사용자 지시 ‘리뷰강화’에 따라 [이미지 전달 전 리뷰 규칙](docs/visual-review-policy.md)을 필수 적용합니다. 이전의 **‘규칙 준수와 제작 방법론만’이라는 제한은 폐기**합니다. 현재 세션과 같은 모델의 독립 외형 리뷰와 독립 기술 리뷰를 모두 수행합니다. 생성·수정한 모든 최종 저장 이미지가 대상이며, 외형 리뷰어는 새 에이전트로 시작해 실제 파일을 엽니다. 외형 첫 판정 전에는 제작자의 성공 평가나 기술 PASS를 제공하지 않습니다. 가능한 경우 `fork_turns="none"`으로 사용자 요구·승인/거절 이력·실제 참고자료·최종 파일만 전달합니다.

외형 리뷰는 품종/개체 특징, 데포르메 안에서의 구조 정합성, 실루엣, 입체 볼륨, 부착부와 표정의 자연스러움을 판정합니다. 기술 리뷰는 출처·추정 구분, 변경 격리, 표면/관절/접촉, 출력 규격과 재현성을 검증합니다. 보호자의 최종 닮음·취향 선택은 대신하지 않지만, 명백한 형태 결함을 ‘미감’이나 ‘사용자 검토 대기’로 넘겨서는 안 됩니다.

전달 가능한 후보는 **TECHNICAL=PASS AND VISUAL=PASS AND 해결되지 않은 BLOCKER/MAJOR=0**인 경우뿐입니다. 미검토·근거 부족·판정 불일치는 전달 차단입니다. 시안·초안·단순화라는 명칭이나 제작자가 정한 좁은 검토 범위로 사용자의 해결 요구를 제외하지 않습니다. 수정 후 바뀐 파일과 영향 범위를 재검토하고, 이전 PASS를 새 이미지에 승계하지 않습니다. 사용자 거절은 해시와 연결된 별도 `review-status.json`에 남기며 생성기가 덮지 못하게 합니다. 최종 전달 전 `python tools/review/check_delivery.py <review-status.json>`을 실행합니다. 이 검사는 기록·해시 확인이며 실제 시각 리뷰를 대신하지 않습니다. 사용자가 실패안·진단 자료를 명시적으로 요청한 경우의 제한된 예외는 위 규칙 문서를 따릅니다.

반복 작화 라운드는 같은 기준안에서 작은 파라미터 차이를 둔 시안 세 개를 병렬로 제작합니다. 각 시안의 변경점과 비교 조건을 기록합니다. 리뷰어는 세 파일에서 선언한 변경만 발생했는지 확인합니다. 규칙 위반은 수정하고, 표현 선택은 보호자가 결정할 수 있도록 분리해 제시합니다. 합친 파일에도 같은 검토를 적용합니다.

새 픽셀 작화에는 전신 외곽선 1색과 내부 최대 4색을 사용합니다. 광원을 정하고 덜 밝은 면을 어둡게 그립니다. 원본 1배에서 움직임과 개체 식별에 필요한 각 신체 부위가 음영이나 윤곽으로 구분되는지 확인합니다.

새 자산을 1배로 기존 자산 옆에서 확인하고, 비교판과 앱의 픽셀 장면은 최근접 이웃·정수 배율로 표시합니다. [격자·윤곽 제작 규격](docs/b2-c2-style-spec.md)의 4.1절을 기준으로 원본, 확대 보기, 실제 기기의 검수 결과를 구분합니다.

개체 이미지 제작은 [화풍 참조 분리 정책](docs/style-reference-policy.md)을 따른다. 현재 구현 순서는 [제작기 로드맵](docs/roadmap.md)이다. 계획된 제작기 실행은 검수된 개체 구조와 버전이 고정된 제작 패키지를 사용하고, 정본 이미지는 패키지 개발·회귀 검수에 사용한다. tools/static_maker에 정적 출력 프로토타입이 있다. 재현성 기술 검사는 통과했지만 정본 미감·개체 닮음은 미승인이므로 전체 제작기 완료로 표시하지 않는다. 다음 실제 이미지 모델 작업에서는 기존 참조 규칙을 유지한다. 사진과 실제 화풍 이미지의 역할·적용 영역을 나누어 도구에 전달하고, 텍스트 화풍 지시만으로 기존 화풍 준수를 주장하지 않는다. 결과의 개체 닮음과 화풍 일치 여부를 별도로 검수한다.

## 구현 기준

- 애니메이션 그림 교체, 입력 처리, 위치 이동, 행동 상태의 시간을 분리합니다. 이동·대기 시간을 프레임 호출 횟수에 종속시키지 않습니다.
- 좌우 비대칭 털무늬를 무조건 반전하지 않습니다. 기준점·캔버스 크기·접지선을 동작 사이에 유지합니다.
- 원본 관찰, 보호자 보고, 파생값, 제작 기본값을 구분합니다. 임시값은 실제 개의 습관으로 표시하지 않습니다.
- AI 후보는 보호자 확인과 근거 검사를 거친 뒤 사용합니다. 확인되지 않은 감정·의도·진단을 추론 결과로 확정하지 않습니다.
- 원본 영상 시각은 실제 타임스탬프를 사용합니다. VFR 영상을 고정 fps로 환산해 측정했다고 주장하지 않습니다.
- 실제 사용자 사진·영상·키·서명 파일은 Git에 넣지 않습니다. 외부 분석용 API 키는 모바일 앱에 내장하지 않습니다.
- 설치·실행하지 않은 코드의 동작, 실측하지 않은 비용·배터리·성능을 완료 결과로 보고하지 않습니다.

## 연구와 선택

관찰·형태와 렌더링·규격 검토는 현재 세션과 같은 모델로 병렬 진행한다. 별도 방법론 자문이 필요하면 `gpt-6-astra`의 `xhigh` 추론 강도를 사용한다.

기술 지원, 라이브러리, 모델 ID, 가격, OS 정책처럼 변할 수 있는 사항은 공식 문서와 실제 사용 버전으로 확인합니다. 조사 저장소의 기능 설명과 프로젝트에서 검증한 성능을 구분하고 출처를 남깁니다. 현재 AI 모델명은 기획 가정이며 G0의 의존성이 아닙니다.

## 변경 관리

리뷰 결과를 받으면 의견별로 사용자 요구, 현재 규격, 실제 변경 내용과 재현 가능한 사례를 대조합니다. 타당하고 현재 작업 범위에서 필요한 수정은 별도 확인을 기다리지 않고 반영한 뒤 검증합니다. 결과를 보고할 때는 반영한 내용과 검증 결과를 밝히고, 채택하지 않은 의견이 있으면 이유를 함께 설명합니다.

작업이 끝나면 `docs/backlog.md`와 `docs/handoff.md`의 상태를 갱신합니다. 새로운 결정은 근거와 함께 `docs/decisions.md`에 기록합니다. `docs/archive`와 `provenance/pages`는 가져온 기록으로 유지하고, 현재 설계 변경은 활성 문서에 작성합니다.

관련 없는 기존 파일을 변경하지 않습니다. 외부 저장소는 참고·도입 후보이며 아직 채택된 의존성이 아닙니다. 프레임워크·라이선스·서비스 범위를 임의로 확정하지 않고, 현재 목표에 필요한 작은 구현부터 진행합니다.
