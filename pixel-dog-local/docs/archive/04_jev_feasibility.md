# Jev와 스마트폰 데이터 기반 반려견 개인화 구현 검토

원본: [ChatGPT 문서](https://chatgpt.com/space/page_10361e1d34e0819198f8de4fe03dd352)  
문서 시퀀스: 0  
내보낸 날짜: 2026-10-17 (Asia/Seoul)

이 파일은 이전 조사·설계의 보존본입니다. 현재 개발 기준은 [결정 기록](../decisions.md)과 [프로젝트 개요](../project-brief.md)를 우선 확인하세요. 내부 프로젝트 링크는 같은 폴더의 문서로 연결했습니다.

스마트폰으로 촬영한 사진·영상·음성, 보호자의 설명과 앱 내 입력을 사용하면 외형과 대표 습관을 반영한 2D 반려견 캐릭터를 구현하는 방향은 현실적입니다. 초기에는 AI가 특징 후보를 정리하고 보호자가 확인한 뒤, 준비된 동작에 개인별 타이밍과 순서를 적용하는 방식이 적합합니다.

Jev는 이 구조에서 상황을 분류하거나 다음 행동을 고르는 판단 모델입니다. 현재 사진·영상·음성을 직접 이해하거나 캐릭터·모션을 생성하는 모델은 아닙니다. 영상 분석과 그림·모션 제작을 다른 구성요소가 담당해야 합니다. [Jev 공식 설명](https://docs.typesafe.ai/concepts/system-one)

검토 기준일은 2026-10-17입니다. 입력은 일반 스마트폰으로 얻을 수 있는 자료에 한정하되 서버의 AI API 사용은 허용하는 조건입니다. 전용 웨어러블, IMU, 압력매트, 모션캡처 스튜디오와 LiDAR 탑재 기기를 필수 조건으로 두지 않습니다.

연결 자료: [프로젝트 범위](./00_project_guidance.md) · [행동 데이터 수집안](./01_data_hierarchy.md) · [2D 3D 애니메이션 문헌](./03_animation_literature.md)

# Jev의 역할과 한계

| 확인 사항 | 공식 문서의 범위 | 프로젝트에 주는 의미 |
|---|---|---|
| 입력 | 텍스트, JSON 객체, 배열. 이미지·음성·영상 미지원 | 영상은 별도 모델로 분석한 뒤 관찰 기록으로 변환 |
| 출력 | 정해진 선택지의 Choice, 등급별 Score, 예·아니오 확률 Noul | 행동 후보 선택·기록 분류·추가 확인 필요 여부에 활용 |
| 생성 기능 | 자유로운 문장·코드·설명 생성 없음 | 캐릭터 이미지·골격·프레임·동작 클립을 만들 수 없음 |
| 개인화 | 고객별 fine-tuning·LoRA 미지원. 상태·지침·판정 기준으로 조정 | 개체 프로필을 앱이 보관하고 관련 정보를 요청에 포함 |
| 확률 | 판단의 불확실성. 집단 수준의 보정이 개별 정답을 보장하지 않음 | 실제 개의 반응률이나 행동 빈도로 대체하지 않음 |
| 언어 | 영어에서 정확도가 가장 높고 다른 언어는 동등하지 않다고 명시 | 한국어 보호자 설명으로 별도 검증 필요 |

근거: [System One](https://docs.typesafe.ai/concepts/system-one), [API reference](https://docs.typesafe.ai/api), [Models](https://docs.typesafe.ai/models).

소개 글의 ‘환각 없음’은 정해진 형식을 벗어나는 출력을 막는 보장과 연결됩니다. ‘접근’과 ‘기다림’ 중 틀린 선택을 할 가능성이 사라지는 것은 아닙니다. 또한 소개 글의 워크플로 평가에는 외부 대형 모델들의 평균 예측을 참조답으로 사용한 조건이 있습니다. 이를 반려견 행동에 대한 관찰자 코딩 정확도나 개체 식별 성능으로 해석할 수 없습니다. [소개 글의 평가 조건](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

예를 들어 Jev가 ‘다가오기’에 0.8을 출력해도 ‘실제 이 개가 80%의 기회에서 다가온다’는 관찰 결과는 아닙니다. 실제 반응률은 같은 상황의 관찰 기회와 반응 횟수로 계산하고, Jev의 확률은 별도의 판단값으로 보존합니다.

# 특징별 현실적인 구현 수준

아래 평가는 현재 지원 기능과 필요한 제작 작업을 바탕으로 한 개발 판단입니다. 정확도 백분율이나 보호자의 개체 인식 성공률을 의미하지 않습니다.

| 특징 | 스마트폰으로 받을 정보 | 현실적인 구현 수준 | 남는 작업 |
|---|---|---|---|
| 털색·무늬·귀·얼굴·체형 | 얼굴·전신·좌우 사진 | 높음: 닮은 2D 캐릭터 초안과 보호자 확인 | 무늬 위치, 반대편 외형, 레이어 분할과 관절 위치 보정 |
| 부르면 바라본 뒤 다가오기 | 호출 전부터 촬영한 영상, 이름·상황 설명 | 높음: 관찰 순서와 대기 시간을 동작으로 연결 | 자극·반응 시작 시각 확인, 무반응·가림 구분 |
| 요구할 때 앞발·코·머리를 쓰는 방식 | 대표 장면 영상과 보호자 지목 | 높음: 준비된 제스처 조합으로 재현 | 동작 라이브러리에 없는 개인 동작은 제작 필요 |
| 음식·장난감 선호와 관심 지속 | 두 상황의 영상, 반복 기록·설문 | 중간 이상: 조건별 반응 차이를 프로필화 | 선택된 성공 영상만으로 선호 강도·확률 확정 불가 |
| 머리 기울임·꼬리 흔들림·몸 흔들기 | 해당 부위가 보이는 짧은 영상 | 중간: 방향·크기·리듬을 근사 | 빠른 동작과 가림은 프레임 확인·보정 필요 |
| 실제 짖음과 소리의 반복 | 자연 발생 음성·상황 | 높음: 원음을 잘라 상황별 재생 | 배경음·말소리 구간 정리. 의미·감정의 확정 해석은 제외 |
| 휴식·활동 시간대 | 보호자 일지, 촬영 시간, 관찰 여부 | 중간: 보고된 일정을 가상 캐릭터에 반영 | 촬영하지 않은 시간의 실제 상태를 자동으로 알 수 없음 |
| 고유한 걸음걸이·좌우 차이 | 전신이 보이는 연속 보행 영상 | 중간 이하: 2D에서 속도·보폭·리듬 근사 | 정밀한 관절·접지 추정과 모션 전이는 별도 개발 |
| 자유 시점의 정확한 3D 움직임 | 일반 사진·단안 영상 | 후속 연구: 형상·골격의 초안은 가능 | 가려진 신체·깊이·체중 이동·털 변형과 개인 모션 검수 |
| 실제 감정·의도·현재 상태 | 일부 장면·보호자 설명 | 제품의 확정 기능에서 제외 | 관찰 행동과 해석을 분리하고 미관측은 미상으로 처리 |

외형 제작은 [이미지 입력을 받아 편집하는 API](https://ai.google.dev/gemini-api/docs/image-generation)로 보조할 수 있습니다. 그러나 출력 이미지가 곧바로 수정 가능한 전신 리그와 동작 클립이 되는 것은 아닙니다. 걷기·앉기·눕기 등 공통 동작을 먼저 제작해 두고, 개인의 외형과 움직임 파라미터를 적용하는 구조가 필요합니다.

영상의 행동 설명·구간 탐색에는 [Gemini 영상 API](https://ai.google.dev/gemini-api/docs/generate-content/video-understanding) 같은 별도 멀티모달 도구를 사용할 수 있습니다. 기본 샘플링이 초당 1프레임이면 빠른 움직임의 세부를 놓칠 수 있으며, 공식 문서도 빠른 동작에 맞춘 프레임률 조정을 안내합니다. ‘꼬리를 흔든다’는 요약과 꼬리의 정확한 주기·각도·발 접지 측정은 다른 과제입니다.

# 스마트폰 입력의 범위

| 입력 | 받을 정보 | 수집 범위의 경계 |
|---|---|---|
| 카메라 | 외형 사진, 행동 영상, 자극·보호자 반응, 관절·윤곽 단서 | 화면 밖, 가려진 부분, 촬영 전후는 관찰 불가 |
| 마이크 | 이름 부르기와 반응의 시간 관계, 실제 짖음·낑낑거림 | 소리만으로 감정·의도를 정답처럼 부여하지 않음 |
| 보호자 입력 | 대표 습관, 선호, 시간표, 맥락, 잘못 추출된 특징의 수정 | 보호자 보고와 영상 관찰을 별도 출처로 저장 |
| 촬영·앱 시간 | 관찰 시각, 앱 입력 시각, 캐릭터 상태 경과시간 | 파일 생성·편집 시각과 실제 촬영 시각을 구분 |
| 앱의 탭·호출 버튼·놀이 제안 | 가상 캐릭터의 행동을 시작하는 이벤트 | 화면의 탭을 실제 개가 쓰다듬어졌다는 관찰로 취급하지 않음 |
| 휴대폰 위치·걸음수·가속도 | 기기·소지자의 움직임 | 개에게 부착하지 않은 휴대폰 값으로 개의 활동량을 대체하지 않음 |

스마트폰만 사용한다는 조건은 충족할 수 있지만, 사진 몇 장만으로 개인 습관을 관찰하는 것은 불가능합니다. 행동에는 영상과 맥락이 필요합니다. 하루 전체의 생활 리듬은 짧은 대표 영상 대신 보호자 일지나 관찰 시간대를 포함한 기록으로 보완합니다.

API에서 관절 좌표를 직접 받는 경로도 플랫폼마다 다릅니다. Apple Vision은 iOS 17부터 개·고양이의 귀·꼬리를 포함한 25개 신체 지점을 이미지·영상에서 찾는 API를 제공합니다. 반면 Google의 기본 MediaPipe Pose Landmarker는 사람 신체용 모델입니다. Android에 같은 개 전용 골격 기능이 그대로 있다고 가정하면 안 됩니다. [Apple Vision](https://developer.apple.com/videos/play/wwdc2023/10045/), [MediaPipe](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker)

양 플랫폼의 첫 공통 버전은 영상 업로드·구간 확인·보호자 수정과 공통 행동 프로필을 중심으로 구성하고, 정밀 자세 추적은 선택 기능으로 분리하는 것이 적절합니다. Android의 [ML Kit 피사체 분할](https://developers.google.com/ml-kit/vision/subject-segmentation)은 반려동물 배경 제거를 지원하지만, 배경 제거와 골격 추적은 별개입니다.

# 권장 시스템 구성

등록할 때는 스마트폰 자료를 분석하고, 사용할 때는 이미 준비된 캐릭터와 동작을 재생하는 두 과정을 분리합니다.

| 구성요소 | 담당 작업 | 실행 시점 |
|---|---|---|
| 스마트폰 수집 화면 | 사진·영상·음성, 상황 설명, 대표성 확인 | 등록·자료 추가 |
| 영상·이미지 분석 API | 관찰 가능한 행동 후보·구간·외형 특징 추출 | 등록·자료 추가 |
| 보호자 확인 화면 | 틀린 후보 수정, 대표 습관 선택, 미상 처리 | 프로필 확정 전 |
| 개체 프로필 | 출처 영상, 확인된 순서·지연·선호·반복, 기본값 구분 | 기기 또는 서버에 보관 |
| 행동 규칙 | 이미 정해진 반응·대기·전환과 관찰 자료 기반 변동 | 기기 내 실행 |
| Jev | 자유로운 설명을 기존 코드로 분류하거나 여러 후보 중 상황에 맞는 행동 선택 | 모호한 입력 또는 필요한 이벤트에 한정 |
| 2D 애니메이션 엔진 | 골격·레이어·준비된 클립을 재생·연결 | 매 프레임, 기기 내 실행 |

Jev에 매 프레임의 관절과 좌표를 생성시키는 구조는 사용하지 않습니다. 클릭에 대한 즉각적인 시각 반응과 모션 보간은 기기가 담당하고, 네트워크 응답이 늦거나 실패해도 기존 행동 규칙이 유지되게 합니다.

고정 버튼 몇 개와 정해진 행동만 있는 첫 버전에는 Jev가 필수적이지 않습니다. 예를 들어 ‘호출 버튼 → 잠깐 보기 → 다가오기’는 프로필과 코드로 실행할 수 있습니다. 보호자가 자유롭게 입력한 설명을 분류하거나 상황 조합이 늘어날 때 Jev의 역할을 비교하는 편이 낫습니다.

Jev에 제공할 행동 후보에는 ‘기존 행동 유지’와 ‘판단 보류’를 포함합니다. 반환된 행동 ID도 현재 자세에서 실행 가능한지, 같은 행동이 과도하게 반복되는지 앱에서 검사합니다. 실제 반려견처럼 보이는지를 결정하는 주요 자료는 개체 프로필과 모션 자산에 있습니다.

# 동작 선택 예시

다음은 실제 관찰 결과나 API 실행 결과가 아닌 설계 예시입니다.

보호자가 확인한 프로필에 ‘이름을 부르면 고개를 돌리고 잠깐 멈춘 후 다가오는 경우가 있다’는 장면을 연결합니다. 영상에서 확인한 대기 시간과 순서를 저장하고, 기본값을 사용한 부분은 표시합니다.

사용자가 호출 버튼을 누르면 현재 캐릭터가 수행 중인 동작을 확인합니다. 고정 규칙으로 처리할 수 있으면 해당 시퀀스를 실행합니다. 상황 해석이 필요한 경우에는 Jev에 현재 가상 상태, 확인된 개인 프로필, 실행 가능한 행동 목록을 보내어 ‘바라보기’, ‘다가오기’, ‘계속 쉬기’, ‘판단 보류’ 중 하나를 고르게 할 수 있습니다.

이때 Jev의 판단 확률과 실제 관찰 반응률은 따로 둡니다. 행동의 재현 빈도를 설정하려면 관찰 기회·횟수가 필요하며, 적은 자료에서는 보호자가 수정할 수 있는 임시 설정으로 관리합니다. 개체 프로필은 앱의 데이터이며, 호출할 때마다 관련 내용을 전달해야 합니다.

# 2D와 3D의 현실적인 경계

2D 우선 선택은 제작 범위를 관리하기에 적합합니다. 옆모습이나 제한된 방향의 캐릭터로 시작하고, 기본 동작에 고개 방향·꼬리 리듬·접근 속도·멈춤·반복·원음을 적용합니다. 처음부터 모든 품종·모든 시점·모든 특이 행동을 자동 처리하는 범위를 약속하지 않습니다.

3D도 스마트폰 사진으로 시작할 수 있지만, 외형 생성·골격 생성·개인 모션 복제는 따로 평가해야 합니다. Tripo의 공식 Auto Rig API는 quadruped를 지원합니다. 확인한 Retarget API의 사족 프리셋 목록에는 quadruped walk가 기재되어 있습니다. 이 지원은 사족 모델을 걷게 하는 출발점이며, 입력 영상에서 해당 개의 실제 습관과 보행을 복사해 준다는 기능은 아닙니다. [Tripo 골격 API](https://developers.tripo3d.ai/en/docs/animations-rig), [프리셋 동작 API](https://developers.tripo3d.ai/en/docs/animations-retarget)

서비스의 웹 기능과 API 지원도 구분해야 합니다. Meshy 웹 가이드는 사족 리깅을 안내하지만, 확인한 Rigging API 문서는 표준 인간형 모델을 지원 대상으로 설명합니다. 이처럼 문서 범위가 다른 경우 API로 동일 기능을 제공한다고 전제하지 않고 실제 요청 시험을 거쳐야 합니다. [Meshy 웹 가이드](https://docs.meshy.ai/en/webapp/guides/animate), [Meshy Rigging API](https://docs.meshy.ai/en/api/rigging)

제품 단계별 현실성은 다음과 같습니다.

| 제품 수준 | 판단 |
|---|---|
| 한 개체의 외형·대표 습관을 제작자가 보정하는 2D 시제품 | 우선 추진할 수준 |
| 준비된 체형·동작 범위 안에서 보호자가 확인하는 반자동 개인화 | 후속 제품 목표 |
| 모든 개의 영상 몇 개를 받아 고유 동작까지 자동 완성 | 정확도·수정 비용 검증 전에는 출시 약속으로 삼기 어려움 |
| 사진만으로 자유로운 3D 움직임과 개인 습관까지 복제 | 현재 자료 조건으로는 목표를 분리해야 함 |

기존 플랫폼 순서는 유지합니다. Android 플로팅의 표시·입력·종료를 먼저 검증한 뒤, 개인화를 적용하고 Android·iOS 공통 앱과 위젯으로 확장합니다. AI API 선택이 운영체제의 표시·백그라운드 제한을 해결해 주는 것은 아닙니다.

# 첫 개인화 실험의 수집안과 제작 범위

다음 수량은 작업량을 제한하기 위한 파일럿 제안이며, 정확도를 보장하는 검증된 최소 수량은 아닙니다.

| 단계 | 스마트폰 수집안 | 목적 |
|---|---|---|
| 첫 초안 | 얼굴·전신·좌우 등 사진 6~8장, 대표 상황 3개의 짧은 영상, 보호자 설명 | 외형과 대표 행동 후보 선정 |
| 반복 확인 | 선정한 상황을 서로 다른 날 추가 촬영하여 상황당 총 3회 정도 확보 | 우연한 한 번과 반복 패턴 비교 |
| 모션 보완 | 옆에서 걷기, 앉기·눕기 전환이 보이는 짧은 영상 | 기본 클립의 속도·자세·전환 보정 |
| 소리 보완 | 자연 발생 원음이 있는 구간 | 실제 소리 재생 |

행동 영상은 15~30초 정도의 구간을 시작점으로 삼되, 자극 전부터 반응과 종료가 담기도록 조절합니다. 반응이 없거나 관찰이 중단된 영상도 구분해 남깁니다. 일반적인 1080p·30fps 촬영을 시작 조건으로 삼을 수 있지만, 털·가림·빠른 움직임에서 부족하면 촬영 조건을 바꾸거나 프레임을 직접 확인해야 합니다.

첫 개인화 결과물의 제안 범위는 한 마리, 제한된 시점, 기본 동작 6~8종, 보호자가 고른 대표 습관 3개입니다. 동작 수는 개발 범위이며 모델의 성능 수치가 아닙니다. 기존 첫 기술 시제품의 걷기·쉬기·잠들기부터 출발하고, 개인화 단계에서 바라보기·앉기·다가오기 등 필요한 동작을 늘립니다.

제작자의 작업은 사라지지 않습니다. 공통 동작과 레이어·골격을 먼저 제작하고, 개체별 외형 오류, 동작 연결, 귀·꼬리·접지와 보호자 피드백을 수정해야 합니다. 특히 매 개체마다 새로운 특이 행동을 제작해야 하는 비율이 서비스의 실제 운영 부담을 결정합니다.

# 비용과 응답 시간의 해석

Jev 공식 가격은 확인일 기준 입력 100만 토큰당 0.042달러이고 출력 토큰은 무료입니다. 예를 들어 청구 입력량이 호출당 2,000토큰이고, 하루 100회, 30일 호출한다고 가정하면 입력량은 600만 토큰, Jev 판단 비용은 0.252달러입니다. 이는 사용량 가정에 따른 계산이며 영상 분석·이미지 생성·저장·서버·통신·제작 인건비를 포함하지 않습니다. [공식 가격](https://docs.typesafe.ai/models)

소개 글의 종단 응답 시간은 70~500ms이며, 공개 평가가 주로 미국 서부에서 수행됐다는 조건을 명시합니다. 한국 스마트폰에서의 전체 지연이나 가용성을 보장하는 수치가 아닙니다. 영상 업로드와 분석 지연은 별도입니다. [속도 조건](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

따라서 영상·이미지 분석은 등록과 갱신 때 수행하고, 평소 동작은 기기에 내려받은 자산과 규칙으로 재생하는 구조를 권합니다. Jev는 필요한 이벤트에서만 호출합니다. 고정 규칙으로 충분한 이벤트까지 계속 호출하면 API 비용과 네트워크 의존성만 늘어날 수 있습니다.

개체당 실제 비용은 첫 파일럿에서 영상 길이, 재분석 횟수, 이미지 재생성 횟수, 개별 보정 시간을 기록한 후 계산해야 합니다. 현재 자료만으로 월 총비용이나 자동화율을 정할 수는 없습니다.

# 파일럿에서 확인할 통과 조건

| 검증 질문 | 확인 방법 |
|---|---|
| 행동 후보를 제대로 추출하는가 | 사람이 코딩한 같은 영상과 비교. 행동 종류·순서·시간을 따로 평가 |
| Jev가 규칙보다 도움이 되는가 | 동일한 입력에 규칙만 사용한 경우와 Jev를 추가한 경우 비교. 오류·보류·지연·수정량 기록 |
| 확률을 신뢰해도 되는가 | 한국어 설명과 실제 개 데이터에서 예측·정답 관계 확인. 판단 확률과 실측 반응률 분리 |
| 그 개의 동작이 보존되는가 | 원본과 클립의 지연·순서·반복·리듬을 대조하고 보호자의 구체적 수정 의견 수집 |
| 보호자가 자기 개답다고 느끼는가 | 외형을 같게 두고 개인 모션과 일반 모션을 비교. 귀여움·자연스러움과 별도 평정 |
| 제품으로 반복 제작 가능한가 | 개체당 사람의 수정 시간, 새 동작 제작 필요 비율, 재생성 횟수 기록 |
| 스마트폰에서 지속 사용 가능한가 | 실제 Android 기기의 표시·입력·종료, 배터리·발열과 API 실패 시 동작 확인 |

Jev의 계정별 요청 한도는 콘솔에서 확인해야 하며, 모델 별칭은 업데이트될 수 있습니다. 비교 실험에서는 버전 ID와 입력·프로필·모션 버전을 기록합니다. Jev의 공식 문서도 별칭 변화에 따라 답변이 달라질 수 있다고 안내합니다. [버전과 한도](https://docs.typesafe.ai/models)

현실적인 첫 목표는 ‘보호자가 확인한 특징을 반영한 2D 개인화 캐릭터’입니다. 원본 행동을 자동으로 완벽 복제하는 수준은 별도 목표로 두고, 먼저 외형·대표 습관·반응 타이밍에서 개체 인식에 도움이 되는 요소를 검증합니다.
